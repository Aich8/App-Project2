# Global Spec: Cash Money Organizer Website

## For who?

This website is for people who keep or manage money in cash and have difficulty organizing it, tracking it, and keeping it under control.

Primary users include:

- People who want to manually track their money amount.
- Students or young adults managing pocket money.
- Small informal sellers or service providers.
- People who do not use a bank account regularly.
- People who want a simple, visual way to update and understand how much cash they have.

## What?

The product is a personal cash management website that looks and feels similar to an online bank account, but it does not hold real money, does not connect to banks, and does not collect personal information.

The exact website name and short trust label shown to the user should be `Manual Cash Tracker`.

Users manually enter and update their own money amount. The website displays a bank-style dashboard with:

- Main money amount shown with the label `Current Balance`.
- `Balance Changes` directly under the main money amount.
- Separate add and subtract history entries.
- `Savings` section with the label `Savings money amount`, ordered user-named `Saving` squares, and coverage bars.

In the first version, clickable controls are specified for mouse clicks and finger taps. Keyboard use is required only for typing inside money amount inputs and `Saving` square inputs, including the specified `Space` key behavior inside main money amount inputs. The first version does not need custom keyboard navigation for clickable controls, custom `Tab` order rules, `Enter` or `Space` activation rules for clickable controls, focus-return rules after save/cancel/delete, or keyboard support for reordering `Saving` squares.

Only one temporary UI should be open at a time. Temporary UI means main money action buttons, a main money amount input flow, a `Balance Changes` delete action square, a `Balance Changes` delete confirmation, a `Saving` square action state, a `Saving` square input flow, a `Saving` square delete confirmation, or an active `Saving` square reorder drag. Full-screen `Savings` is the current view while it is open, not a temporary UI layer; opening it from the dashboard should be allowed only when no dashboard temporary UI is open. If a temporary UI is open, the user should close, cancel, save, delete from, finish, or drop/cancel it before another temporary UI can open. A click, tap, or hold that would normally open a different temporary UI should not open that new temporary UI while another one is already open. If that same click or tap closes or cancels the open temporary UI because of an outside-click rule, it should only close or cancel the open temporary UI and should not also activate the thing behind it. Actions inside the current temporary UI may replace it with the next step of the same flow, but the previous temporary UI should close or be replaced first so only one temporary UI is visible at once.

If the user refreshes the page, closes the browser tab or window, or reopens the website later while any temporary UI is open, the website should silently discard that temporary UI and return on the next load with the latest successfully saved data and no temporary UI open. It should not restore open temporary UI, save unsaved typed input, confirm pending deletes, save pending reorders, create a `Balance Changes` entry, show a message, or show a browser leave warning.

The main money amount is clickable. When the money amount is `0.00$`, clicking it shows `Add` and `Modify`, but not `Subtract`. When the money amount is greater than `0.00$` and less than `999,999.99$`, clicking it shows `Add`, `Subtract`, and `Modify`. When the money amount is exactly `999,999.99$`, clicking it shows `Subtract` and `Modify`, but not `Add`. The visible main money actions should be buttons lined together horizontally near the main money amount. When `Subtract` is hidden at `0.00$`, the visible order should be `Add`, then `Modify`. When all three actions are visible, the left-to-right order should be `Add`, `Subtract`, and `Modify`. When `Add` is hidden at `999,999.99$`, the visible order should be `Subtract`, then `Modify`. The main money action buttons should not appear as a modal, bottom sheet, separate page, or large expanded area. If the main money action buttons are visible and the user clicks or taps the main money amount again, the buttons should go away without changing the money amount, saving anything, creating a `Balance Changes` entry, or showing a message. If the main money action buttons are visible and the user clicks or taps outside the main money amount and outside the visible action buttons, the buttons should go away without changing the money amount, saving anything, creating a `Balance Changes` entry, or showing a message. If the main money action buttons are visible and the user scrolls the dashboard page, the buttons should go away without changing the money amount, saving anything, creating a `Balance Changes` entry, or showing a message. Clicking `Add`, `Subtract`, or `Modify` should start that selected money amount input flow and should not be treated as an outside click. When the selected input flow starts, the visible main money action buttons should go away, the selected action should be remembered internally only, and the open input flow should not show a visible reminder of whether the user selected `Add`, `Subtract`, or `Modify`.

The user opens `Savings` by clicking `Savings`. There should not be a separate `Open savings` action. When opened, `Savings` should take the entire screen and show the `Savings money amount` with the `Saving` squares. A small `<` sign should appear in the top-left corner of the full-screen `Savings` view. When no `Saving` square input flow or `Saving` square delete confirmation is open, clicking `<` should return the user to the dashboard without changing anything, saving anything, or creating a `Balance Changes` entry. Using the browser Back button, mobile browser back gesture, or system Back action while the full-screen `Savings` view is open should also close `Savings` and return to the dashboard when no `Saving` square input flow or `Saving` square delete confirmation is open, without changing anything, saving anything, creating a `Balance Changes` entry, or showing a message. If a `Saving` square create, rename, planned-money-amount change, or broken-square fix input flow is open, clicking `<` or using Back should close that input flow first, act like `Cancel`, keep the user inside `Savings`, discard the unsaved typed input, restore the `+`, normal square, or broken square that the input replaced, change nothing, save nothing, create no `Balance Changes` entry, and show no message. If a `Saving` square delete confirmation is open, clicking `<` or using Back should close that confirmation first, keep the user inside `Savings`, delete nothing, change nothing, save nothing, create no `Balance Changes` entry, and show no message; a normal selected square should return to default state and a broken selected square should stay visible. After the open input flow or delete confirmation is closed, clicking `<` or using Back again should close full-screen `Savings` if no other `Saving` square input flow or delete confirmation is open.

The top `Savings` area with the small `<` sign and the `Savings money amount` should stay fixed at the top of the full-screen `Savings` view while the user scrolls through `Saving` squares. Only the `Saving` squares area should scroll below it, without hidden square content.

`Savings` is the separate planning section of the website. A `Saving` is one user-named square inside the `Savings` section.

In the first version, `Saving` squares should not save or show a created date or updated date.

Visible `Saving` squares should appear in one vertical column on mobile and desktop, not in multiple columns or a grid. Coverage order should be the visible top-to-bottom column order.

In its default state, each visible `Saving` square should show the `Saving` name in the top-left corner, the planned money amount on the right side of the same top row, and the thin coverage bar at the bottom. Clicking a `Saving` square should change that same square into its action state. For touch users, moving the finger more than `8px` before the finger is lifted and before the `600ms` reorder hold completes should count as scrolling, should cancel the pending tap and any pending reorder hold, should not open the action state, should not start reorder, should not change or save anything, should not create a `Balance Changes` entry, and should show no message. If the finger is lifted before `600ms` without moving more than `8px`, the touch should count as a tap and should open the action state. If a touch or mouse user holds for `600ms` but releases before moving at least `8px`, nothing should happen: no action state, no reorder, no drag placeholder, no saved change, no `Balance Changes` entry, and no message. In the action state, the square should still show the `Saving` name and planned money amount, should show `Delete` at the bottom center, and should hide the thin coverage bar. In the action state, clicking the `Saving` name should open rename, clicking the planned money amount should open planned-money-amount change, and clicking `Delete` should start delete confirmation. The website should not use a separate action menu or larger action square for those three actions. The `Saving` square delete confirmation should appear as a small confirmation square in the middle of the screen with `Delete this Saving?`, `Cancel`, and `Delete`; only one `Saving` delete confirmation should be open at a time. Clicking `Cancel` or outside that small confirmation square should close it, change nothing, save nothing, create no `Balance Changes` entry, and show no message. Clicking `Delete` in the small confirmation square should close it and delete only the selected `Saving` square. Rename and planned-money-amount change should each replace that same `Saving` square with a temporary `Saving` input square in the same visible position, not a modal, bottom sheet, separate page, or separate floating input. The rename input square should ask only for the new `Saving` name. The planned-money-amount change input square should ask only for the new total planned money amount. If a `Saving` square is in action state and the user clicks or taps outside that same square, the action state should close, change nothing, save nothing, create no `Balance Changes` entry, and show no message. Clicking inside the open square should not count as an outside click. Clicking or tapping a blank part of the same open action-state square should do nothing: the square should stay in action state, nothing should change, nothing should save, no `Balance Changes` entry should be created, and no message should appear. Clicking another normal default `Saving` square should close the old action state, but the clicked square should not open from that same click; the user can click it again after no temporary UI is open. Scrolling alone should not close the action state. Clicking `<` should clear any open action state as part of returning to the dashboard.

The user creates a `Saving` square by clicking the circle `+` action in `Savings`. The create flow should replace the clicked `+` with a temporary `Saving` input square inside the `Saving` squares area, either centered when the empty-state `+` was centered or at the top-left before existing squares when the `+` was in the top-left. The temporary square should ask for the square name and planned money amount before a normal square appears. It should not open as a modal, bottom sheet, or separate page.

When no normal `Saving` squares and no broken saved `Saving` squares are visible, the circle `+` action should appear centered in the `Saving` squares area and serve as the empty state. The website should not show a separate empty-state sentence for no `Saving` squares. After at least one normal `Saving` square exists, the circle `+` action should appear at the top-left of the `Saving` squares area, above or before the squares, so the user can add more `Saving` squares. A broken saved `Saving` square should count as a visible square for circle `+` placement only, so if only broken saved `Saving` squares are visible, the circle `+` should appear at the top-left above or before those broken squares. Broken saved `Saving` squares should still not affect `Savings money amount`, top needed text, or coverage bars.

If the user tries to save a new `Saving` square without a planned money amount, the website should do nothing: no message, no new square, no saved data change, and the create flow stays open until the user enters a planned money amount or cancels.

A `Saving` square name is required and must be unique inside `Savings`. The website should not create, rename, or fix a `Saving` square with the same name as another normal `Saving` square or a visible broken saved `Saving` square whose saved name can be read and is not empty after trimming spaces, using trimmed names and ignoring uppercase or lowercase letters when checking for duplicates. During a broken-square fix, the broken `Saving` square being fixed should not count as a duplicate against itself, but normal `Saving` squares and other broken `Saving` squares with the same trimmed name should still block the fix.

`Saving` square names should not have a maximum length. The user can use one letter, only numbers, numbers before or after words, multiple words, full sentences, symbols, punctuation, emoji characters, or very long names. The website should trim spaces at the beginning and end before saving the name, but spaces inside the trimmed name should stay.

Very long `Saving` square names should wrap or otherwise stay contained inside the square layout. A long name should not create horizontal page overflow, overlap other square content, or be rejected only because of its length.

If the user tries to save a new `Saving` square without a `Saving` name, the website should do nothing: no message, no new square, no saved data change, and the create flow stays open until the user enters a name or cancels.

If the user tries to rename an existing `Saving` square with an empty name, the website should do nothing: no message, no saved data change, and the rename flow stays open until the user enters a name or cancels.

If the user enters a duplicate `Saving` name while creating, renaming, or fixing a `Saving` square, the website should return to the `Saving` squares view without showing a duplicate-name error message. Nothing should change.

If saved browser data can be loaded but one saved `Saving` square is broken, the website should keep the rest of the saved data and show that broken square in `Savings` with the exact text `Saving could not be loaded.` and actions exactly named `Fix` and `Delete`. A broken `Saving` square should not use money amount inside `Savings`, should not lower the `Savings money amount`, should not show a top needed text, should not show a coverage bar, and should not affect coverage bars for valid `Saving` squares until fixed. A broken `Saving` square should stay locked in its current displayed position until fixed or deleted, should not be draggable, and should not be reordered. Normal default `Saving` squares can still be reordered while broken `Saving` squares are visible, but broken squares stay in their displayed positions and continue to be skipped by `Savings money amount`, top needed note, and coverage calculations. `Fix` should change the broken square into a temporary `Saving` input square in the same visible position, ask for a valid `Saving` name and planned money amount greater than `0.00$` and not greater than `999,999.99$`, and should not open as a modal, bottom sheet, or separate page. A fixed `Saving` square should stay in the same visible position when possible and get a valid unique ID and valid order if needed. `Delete` should use the same small centered `Saving` delete confirmation with `Delete this Saving?`, `Cancel`, and `Delete`. Fixing or deleting a broken `Saving` square should save the change, recalculate the `Savings money amount`, top needed text, and coverage bars, create no `Balance Changes` entry, and update no other `Saving` squares.

If saved browser data can be loaded but one saved `Balance Changes` entry is broken, the website should keep the rest of the saved data and remove only the broken history entry. It should not show the full saved-data error message, should not show a broken history row, should not change the main money amount, should not change `Savings`, and should show no message to the user.

The money amount shown at the top of `Savings` should use the exact user-facing label `Savings money amount`. This label is separate from `Current Balance`, which is only for the main money amount.

When `Savings money amount` is `0.00$`, it should keep the same visual style as other `Savings money amount` values. The website should not make `0.00$` look like a warning or error, and should not add a message only because the value is `0.00$`.

When total planned money amount in valid `Saving` squares is greater than the main money amount, the top `Savings` area should show small text directly under `Savings money amount` in the format `{money amount} needed`, such as `20.00$ needed`. The amount should be the difference between total planned money amount in valid `Saving` squares and the main money amount. Do not show this top needed text when total planned money amount in valid `Saving` squares is equal to or less than the main money amount.

While a `Saving` square input flow is open, the `Savings money amount`, top needed text, and coverage bars should stay based on saved data only. They should not preview unsaved typed input, and should update only after a successful `Save`.

The `Savings` section checks `Saving` squares from top to bottom against the main money amount. In easy terms, the money amount shown inside `Savings` goes to the visible `Saving` squares in order until no more money amount is left to plan. Each square keeps the planned money amount chosen by the user and shows a thin bottom coverage bar in its default state so the user can see whether that square is fully covered, partly covered, or not covered. The bar is grey by default and fills green from left to right as coverage increases. If a square is not fully covered, its `{money amount} needed` note appears at the top-left of the bottom coverage bar.

The visible order of normal `Saving` squares is the coverage order. If the user moves a normal `Saving` square to the top, that square is checked first, so its coverage bar fills from the main money amount before lower normal squares use what remains. Touch users should reorder a normal default `Saving` square by holding the whole square for `600ms`, then moving it. Mouse users should reorder by clicking and holding the whole square for `600ms`, then dragging it. Broken `Saving` squares should not be draggable and should not be part of the reorder action until fixed. For touch users, moving the finger more than `8px` before the `600ms` hold completes should count as scrolling and should cancel the pending reorder hold. After the `600ms` hold completes without being canceled, dragging should start only after the pointer or finger moves at least `8px`. If a touch or mouse user holds for `600ms` but releases before moving at least `8px`, nothing should happen: no action state, no reorder, no drag placeholder, no saved change, no `Balance Changes` entry, and no message. Holding or dragging a normal `Saving` square should not open rename, planned-money-amount change, or delete. While dragging, the dragged normal square should follow the user's finger or mouse pointer, and the old position should show a placeholder the same size as the dragged square. During reorder, auto-scroll should start when the user's finger or mouse pointer is within `40px` of the top or bottom edge of the scrollable `Saving` squares area. Auto-scroll should use a fixed speed of `8px` per animation frame, top and bottom should use the same trigger distance and speed, and the speed should not change based on how close the finger or pointer is to the edge. If the user's finger or mouse pointer leaves the screen, the browser window loses focus, or the drag is interrupted before the square is dropped, reorder should be canceled; the square should return to its original position, the drag placeholder should be removed, any reorder auto-scroll should stop, nothing should save, no `Balance Changes` entry should be created, and no message should appear. Reordering should be disabled while any `Saving` square is in action state, input state, or delete confirmation state; the user should close, cancel, save, or finish that state before reordering. When the user finishes moving a normal square and lets go, the website saves the new normal square order and recalculates the `Savings` display from that order while skipping broken squares.

The planned money amount in a `Saving` square does not mean money has moved into a separate place. It does not lower the main money amount.

After a `Saving` square is created, changing its planned money amount replaces the old planned money amount with a new total planned money amount. It is not an add or subtract action and does not change the main money amount.

If the user tries to change an existing `Saving` square's planned money amount with an empty planned money amount or a planned money amount greater than `999,999.99$`, the website should do nothing: no message, no saved data change, and the change flow stays open until the user enters a valid planned money amount or cancels.

A `Saving` square should not be created or saved with a `0.00$` planned money amount or a planned money amount greater than `999,999.99$`. If the user tries to save a new `Saving` square with a planned money amount of `0.00$` or greater than `999,999.99$`, nothing should happen: no message, no new square, no saved data change, no `Balance Changes` entry, and the same `Saving` square create input step stays open until the user enters a planned money amount greater than `0.00$` and not greater than `999,999.99$` or cancels. If an existing `Saving` square's planned money amount becomes `0.00$`, the square should disappear from `Savings`.

When a new `Saving` square create attempt has more than one invalid value, the website should check the planned money amount first, the missing `Saving` name second, and the duplicate `Saving` name third. If the planned money amount is missing, `0.00$`, or greater than `999,999.99$`, the same `Saving` square create input step should stay open with no message, no saved data change, no new square, and no `Balance Changes` entry, even if the entered name is also duplicate.

When a broken-square fix attempt has more than one invalid value, the website should use the same order: planned money amount first, missing `Saving` name second, and duplicate `Saving` name third. If the planned money amount is missing, `0.00$`, or greater than `999,999.99$`, the same broken-square fix input step should stay open with no message, no saved data change, no fixed square, and no `Balance Changes` entry, even if the entered name is also missing or duplicate.

Deleting a `Saving` square removes only that square and its saved details. It does not change the main money amount, `Balance Changes`, or the other `Saving` squares. The money amount shown inside `Savings` and coverage bars update from the remaining squares because they are calculated display values.

Deleting a `Saving` square should ask for confirmation in a small confirmation square in the middle of the screen with the exact message `Delete this Saving?` and buttons exactly named `Cancel` and `Delete`. Only one `Saving` square delete confirmation should be open at a time. Clicking `Cancel` or clicking outside the small confirmation square should close it, change nothing, save nothing, create no `Balance Changes` entry, and show no message.

There is no separate `View history` action. `Balance Changes` should sit directly under the main money amount as a large square that takes most of the dashboard page space under the main money amount. `Balance Changes` entries should scroll inside that square when they are too long to fit. The dashboard page itself should still scroll down past the large `Balance Changes` square to reach `Savings`, which appears below that square. Scrolling that starts inside the large `Balance Changes` square should stay inside that square, even when the internal entry list is already at the top or bottom. To scroll the dashboard page down to `Savings` or back up, the user should scroll outside the large `Balance Changes` square. Every valid 30-day `Balance Changes` entry should remain available inside the scrollable square, with no smaller maximum visible-entry limit.

Visible money amounts should use two digits after the decimal point, such as `0.00$`, `5.00$`, and `14.50$`. Visible money amounts of `1,000.00$` or more should use comma separators every three digits before the decimal point, starting from the right, such as `5,895.50$` and `999,999.99$`.

Saved browser storage money amount values should use normalized plain decimal strings without the `$` sign or comma separators, such as `0.00`, `5.00`, `5895.50`, and `999999.99`. User-facing website display should still add comma separators and the `$` sign, such as `5,895.50$`.

Money amount values can include cents, but the maximum allowed money amount is `999,999.99$`. The main money amount and each `Saving` square planned money amount should never be saved above `999,999.99$`. Examples of valid visible money amounts include `5.05$`, `0.05$`, and `999,999.99$`. Values above `999,999.99$` are invalid.

When no saved money amount exists yet, the website starts with the money amount at `0.00$` and shows the dashboard. This default `0.00$` amount does not create a `Balance Changes` entry.

Opening the website with the default `0.00$` money amount should not create saved browser data by itself. The website should start saving after the first successful saved user action. In the normal first money flow, this is the first successful `Add`.

If browser storage is unavailable, full, blocked, or fails while saving a valid user action, the website should block that action, keep the visible website state on the last successfully saved data, and show the exact message `Changes could not be saved.`. A user action should count as successful only after browser storage saves it. On save failure, main money amount inputs and `Saving` square input flows should stay open with the same typed values, delete confirmations should stay open with the selected item still visible, and a failed `Saving` square reorder should return to the last successfully saved order.

The user clicks the money amount and uses `Add` to add money while the money amount is below `999,999.99$`. Users can use `Modify` at `0.00$` or any other valid money amount. After the money amount is greater than `0.00$` and less than `999,999.99$`, users can update the amount with `Add`, `Subtract`, and `Modify`. At exactly `999,999.99$`, users can still use `Subtract` and `Modify`, but cannot use `Add`.

Main money action inputs for `Add`, `Subtract`, and `Modify` should open as a horizontal money amount input square in the middle of the screen, with the main money amount circle still visible only as a dimmed, inactive background element. The input flow should be the active part of the screen. Clicking or tapping the visible main money amount circle behind the input flow should act like `Cancel`: the input flow should close, the dashboard money amount view should return, nothing should change, nothing should save, no `Balance Changes` entry should be created, and no message should appear. Clicking or tapping the visible main money amount circle should not reopen the main money action buttons. Using the browser Back button, mobile browser back gesture, or system Back action while a main money action input is open should act like `Cancel`: the input flow should close, the dashboard money amount view should return, nothing should change, nothing should save, no `Balance Changes` entry should be created, and no message should appear. Refreshing the page, closing the browser tab or window, or reopening the website later while a main money action input has unsaved typed input should discard that input state and typed value. The next load should show only the last successfully saved data, with no save, no `Balance Changes` entry, and no message or browser leave warning. The square should start by showing `0.00` without the `$` sign. When the horizontal input square opens, it should be focused and ready for typing immediately. On supported mobile devices, opening the input flow should request the mobile keyboard immediately. The user should type only the money amount, without the `$` sign. Main money amount inputs should request a mobile keyboard suitable for digit entry on supported devices. All users should be able to enter cents with `Space` or with a rectangular `Cent` button shown as part of the main money amount input controls while a main money amount input is open. The `Cent` button should appear directly under the horizontal input square on mobile and desktop. On mobile, when the browser and keyboard allow it, this placement should also keep the `Cent` button directly above the mobile keyboard. The `Cent` button should behave the same as pressing `Space`, should not add visible text to the input, and should not cancel or close the input flow. The user should not enter cents in main money amount inputs by typing a decimal point.

Main money amount inputs should accept only numbers from `0` through `9` and separator input from the `Space` key or `Cent` button. Typed decimal points, comma separators, `$` signs, letters, minus signs, starting separators, consecutive separators, additional separators after two accepted separators, a third cents digit after the cents group is fixed by two accepted separators, paste, and other blocked input should not change the field and should show no message. The decimal point and comma separators in the displayed input should be generated by the website only.

For accepted input without separator input, all digits are whole money amount digits: typing `5` should show `5.00`, `58` should show `58.00`, `589` should show `589.00`, `5895` should show `5,895.00`, `58955` should show `58,955.00`, and `589550` should show `589,550.00`. `0` is a normal digit, not a starting zero-position skip, and unneeded leading zeros in the whole money amount should be normalized away, so typing `0005` should show `5.00`.

The `Space` key and `Cent` button should act as a non-visible separator between digit groups. A separator should be accepted only after at least one digit and only when the previous accepted input is a digit. If the input ends with a separator, all completed digit groups should be treated as the whole money amount and cents should show as `00`. If the final group after a separator has one or two digits, that final group should be treated as cents and should be left-padded with `0` when it has one digit. All earlier groups should be joined together as the whole money amount. If there is only one accepted separator and the final group grows to three or more digits, that final group should be treated as another whole money amount group and cents should show as `00`. Once the input has two accepted separators, the final group is the cents group and should accept at most two digits. Additional `Space` key presses or `Cent` taps after two accepted separators should be blocked with no message.

Examples: typing `5`, then `Space`, keeps the display at `5.00`; typing `5`, then `Space`, then `5` shows `5.05`; typing `5`, then `Space`, then `50` shows `5.50`; typing `58`, then `Space`, then `430` shows `58,430.00`; typing `58`, then `Space`, then `430`, then `Space`, then `88` shows `58,430.88`; typing `0`, then `Space`, then `5` shows `0.05`; typing `999999`, then `Space`, then `99` shows `999,999.99`; and typing `Space`, `Space`, `Space`, then `5` blocks the three `Space` key presses and then shows `5.00` after the `5` is typed. Tapping or clicking `Cent` should work the same as pressing `Space`, so typing `5`, then choosing `Cent`, then typing `50` should show `5.50`.

If the user deletes one typed character, the website should remove the last accepted digit or accepted separator, then format the remaining accepted input again with two digits after the decimal point, automatic comma separators when needed, and no `$` sign. If the user deletes all typed numbers, the square should return to `0.00` and should not become empty.

The main money amount input is append-only: focus is allowed, but users should not move the cursor into the formatted value, select part of it, replace selected text, or edit generated comma separators or the generated decimal point. Accepted typing goes to the end, and delete removes only the last accepted digit or accepted separator.

If an `Add` action would make the main money amount greater than `999,999.99$`, the website should do nothing: no message, no saved data change, no `Balance Changes` entry, and the same money amount input step stays open. Money amounts up to `999,999.99$` should stay editable in the horizontal input square with required comma separators while typing and readable on the dashboard with required comma separators after saving, without horizontal page overflow, overlapping other content, or hiding actions. Under the square, the website should show the rectangular `Cent` button. Under `Cent`, the website should show `Save Changes`, with buttons exactly named `Yes` and `Cancel` under `Save Changes`. `Yes` should try to apply the selected action, `Cancel` should close without changing anything, and clicking or tapping outside the horizontal input square, `Save Changes`, `Yes`, `Cancel`, and the `Cent` button should act like `Cancel`, including clicking or tapping the dimmed, inactive main money amount circle behind the input flow. ## Why?

Cash is easy to spend because it is not automatically tracked. Users may forget how much money they received, how much they spent, and what cash they meant to keep aside.

The website helps users:

- See their money amount with a familiar bank-style `Current Balance` label.
- Manually modify their money amount at any valid money amount, using any corrected value from `0.00$` through `999,999.99$`.
- Add money and subtract money while keeping each change visible on its own.
- Correct mistakes with `Modify` at any valid money amount, without saving or showing a correction entry.
- Correct their money amount with `Modify` at any valid money amount, including correcting it to `999,999.99$`.
- Plan savings with user-named `Saving` squares that show covered and needed money without lowering the main money amount.
- Understand where their cash is going.

The goal is to make cash feel organized, visible, and easier to control.

## Where?

The website is used in a browser on desktop and mobile.

Users should be able to open it quickly when they want to check or modify their money amount, especially from a phone.

Users may update their money rarely or many times in one day. The website should not require a specific update schedule.

If the user closes the website and opens it again later, their saved money amount and 30-day visible history should still appear when the saved data is available.
